# 评测集 v2：20 组真实资料评测设计

日期：2026-11-24。状态：待用户审阅。

## 1. 目的

为答辩准备一套**能讲清楚**的评测：评委能看到系统在哪些能力上可靠、哪些不足、失败原因是什么
（评分卡“评测与解释 10%”）；并保留一小部分题用于比较算法改动（“算法拓展 10%”）。

评测集与答辩演示分开：

- **评测集**：20 组详细评测，全部可复现，最终产出一份评测报告。
- **演示**：从 20 组中挑 1～2 组现场跑，结果出来后再定（初选：法规库多轮追问、基金库多文档对比）。

## 2. 目标、非目标、反目标

目标：

1. 6 个真实公开资料知识库，尽量丰富（同主题多文档、天然干扰项），覆盖 PDF / DOCX / TXT。
2. 20 组场景，每组 3～6 题（含多轮追问），合计约 80～110 题，覆盖第 4 节的 9 个维度。
3. 每题逐要点标注：回答信号、必需证据（文件 + 位置 + 原文锚点）、计算（Decimal 复算）。
4. 自动规则 + 模型评审 + 人工抽检三层判分，报告同时给出“规则通过”与“语义通过”。
5. 一个标注“对比用”的算法对比子集，在其上比较检索策略与优化前后效果。
6. 生成一份供用户人工审阅的题目文件；未审阅的题不计入最终报告。

非目标：

- 旧 `eval/cases.jsonl` 20 题（虚构语料）降级为 pytest 回归用例，不进入 v2 报告。
- 系统行为（删除同步、重启不丢、解析失败可重试、幂等）不在评测集里出题，继续由 pytest 保证；
  报告附一张“任务书验收项 → 对应测试”对照表。
- 不做在线评测、不做微调、不新增产品功能。

反目标（即使跑通也算失败）：

- 生成、改写或重新排版资料冒充真实资料。
- 把模型起草、未经人工审阅的答案当金标准。
- 用测试集（`split=test`）反馈调参，或把 `rule_passed` 写成最终正确率。
- 把原始资料全文提交进仓库；在结果、日志里写入密钥或服务地址。

## 3. 知识库（全部真实公开资料）

| ID | 知识库 | 来源 | 格式 | 目标规模 | 主要用途 |
| --- | --- | --- | --- | --- | --- |
| KB1 | 基金定期报告 | 现有易方达 510100 / 510310 四份季报，扩充到 4～6 只宽基 ETF（易方达、华夏、华泰柏瑞等）× 2024Q4～2025Q3 | PDF | ~20 份 | 数值、跨期、多文档对比、引用聚合 |
| KB2 | 上市公司年报 | 交易所披露的金融类上市公司年报（如银行、保险、券商），2～3 家 × 1～2 年 | PDF | 4～6 份（每份上百页） | 长文档分页读取、表格、跨公司对比 |
| KB3 | 金融法规 | 国家法律法规数据库（《证券法》《证券投资基金法》含修订前后版本）、证监会规章（公募基金运作、信息披露、指数基金指引等） | DOCX 优先；原文只有 PDF 的保留 PDF | ~20～30 部 | 条款定位、相似条文干扰、版本对比、多轮追问、与 KB1 跨库关联 |
| KB4 | 统计公报 | 国家统计局历年《国民经济和社会发展统计公报》 | TXT（官网正文原样保存） | ~10 年 | 年度对比、计算、口径变化、部分缺失 |
| KB5 | AI 英文论文 | arXiv 上 CC BY 许可的 RAG / LLM Agent 论文 | PDF | 8～12 篇 | 中文问英文（跨语言）、方法与实验对比、表格数字 |
| KB6 | 多跳 QA | MuSiQue（CC BY 4.0，含不可回答题）、HotpotQA distractor（CC BY-SA 4.0）抽样题目对应的维基段落，按条目每篇一个文件 | TXT | 抽样 ~200 题，对应约 1000～2000 篇 | 多跳推理、比较、不可回答；外部金标准；算法对比子集主体 |

KB1、KB2、KB3 同属金融主题，天然互相干扰，用于范围隔离。

资料规则（沿用 `eval/finance`）：

- 每个库一个 `manifest.json`：来源 URL、获取日期、SHA-256、字节数、页数/行数、许可或权利说明。
- 原文由脚本下载到已忽略的 `eval/results/` 下，仓库只存元数据、标注和最小证据锚点。
- 格式转换只允许“原样保存”：KB4 网页正文保存为 TXT、KB6 段落按条目拼成 TXT，不改写内容，
  在 manifest 中标明 `source_type`。
- 每个来源的许可在构建时逐一核实；许可不明的不用。

## 6. 出题与标注流程

- **自建库（KB1–KB5）**：模型起草 → 程序核验 → 人工审定。
  1. 构建会话中由 Claude 读原文，起草问题、要点、证据锚点、计算和参考答案。
  2. 程序核验：锚点在所标文件的所标页/段/行原文中存在；数值与计算可复算；
     证据文件都在本组所选知识库内；结构合法。核验不过的题不进入审阅。
  3. 生成审阅文件（每组一节，含问题、参考要点、证据原文摘录、考察维度），交用户人工审阅；
     每题记录 `review: pending | approved | revised | rejected`。
- **KB6**：问题、答案、支撑句直接取自数据集，不改写；支撑句映射为 TXT 文件 + 行号作为证据锚点。
  答辩组 G17–G18 从抽样题中挑选；完整抽样（~200 题）作为算法对比子集。
- 任何金标准修改都记录原因；不为迁就实现修改标注。

## 7. 判分

三层，报告分别列出：

1. **规则信号**：推广 `eval/finance/scoring.py`，证据匹配支持全部 4 种位置
   （`pdf_page`、`docx_paragraphs`、`docx_table_rows`、`txt_lines`）；数值信号保留符号、量级、单位；
   结构检查（正常结束、SSE 顺序、范围、引用标记唯一）。
2. **模型评审**（与作答模型 `deepseek-v4-pro` 不同家，避免自评偏好）：
   - **在 Claude Code 会话内评审，不调用 API、不需要额外密钥**（本机无 Anthropic API 凭据）。
   - 评测运行后，脚本为每组生成“评审包”JSON：问题、参考要点、证据原文摘录、模型回答、引用快照、
     规则信号。评审包不含密钥和服务地址。
   - 初审：会话中按组派发 Sonnet 5.5 子 Agent，逐要点判定，写出判定文件：
     `correct`（对/错/部分）、`citation_supports`（支撑/不支撑/无引用）、`reason`（中文，一两句）、
     `judge_model`。脚本校验判定文件结构，缺项、多项或格式不对的整组重判。
   - 复审：Opus 5.5 只复审三类要点：初审与规则信号矛盾、初审为“部分”、初审缺失或无法判定。
     复审结果覆盖初审，两次判定都保留。
   - 评审说明（`eval/suite/judge/PROMPT.md`）与判定格式入库并记入数据集指纹；改动后必须重判，
     不与旧判定混用。报告注明“评审在 Claude Code 会话内完成”，他人可用同一说明和评审包复核，
     但不是一条命令即可自动复跑的步骤。
3. **人工抽检**（用户执行）：从全部要点中分层抽取约 20%（每组至少 1 个、覆盖每个维度），
   加上第 2 层标记需要人工的要点，生成抽检表；用户填写判定后，报告给出评审与人工的一致率
   （逐项一致率 + Cohen's κ），被抽检的要点以人工判定为准。

每组主配置（hybrid）重复 3 次，报告均值、波动和 pass^3；通过率附 Wilson 95% 区间。

## 8. 算法对比子集

- 检索层（无聊天模型）：KB6 ~200 题 + 各组中标“对比用”的题，比较 cosine / bm25 / vector / hybrid
  及 D4 算法改动前后；指标 Recall@k、MRR、nDCG@10、证据组覆盖；配对 bootstrap 给出差值区间。
- Agent 层：只在标“对比用”的 dev 组上比较 2 个配置，各跑 3 次。

## 9. 运行与报告

- 入库一次、多次复用：首次运行把全部知识库经真实 HTTP 上传入库，保存数据目录快照；
  每次评测复制快照到新的临时目录（长年报 Docling 解析耗时长，不能每次重解析）。
- 结果写 `eval/results/suite/`（已忽略），记录数据集指纹、配置、逐题明细。
- 报告重写 `docs/eval-report.md`，旧 D2 基线报告移到 `docs/eval-report-d2.md`。结构：
  数据集与来源 → 维度 × 组覆盖矩阵 → 总体结果 → 分维度 → 分组 → 算法对比 → 失败分析（按失败类型） →
  成本与延迟 → 局限与未覆盖。

## 10. 约束

- 只用公开资料；密钥只走环境变量；离线 pytest 不依赖网络和模型（缺原文时跳过来源核验，与 finance 一致）。
- 不新增依赖；数据集下载用现有 `httpx`，模型评审在会话内完成。
- 人工工作量：用户审阅全部题目（约 80～110 题），并抽检约 20% 的要点判定。
- `eval/**`、`docs/eval-report.md` 属 D 所有（`docs/tasks.md` §2）。
- 时间：D4 需要基于 dev 结果做算法优化，D5 答辩；组装顺序见第 11 节。

## 11. 交由实现者决定

- 目录结构（建议 `eval/suite/kbs/<KB>/`、`eval/suite/groups/`、`eval/suite/REVIEW.md`）与代码复用方式
  （复用 `eval/finance` 的 dataset/scoring，保持其现有测试通过）。
- 具体基金、公司、法规、年份、论文的选择，以来源可下载、许可清楚、互相有干扰为准。
- 推荐顺序：资料下载与核验 → 出题与程序核验 → 交用户审阅 → 判分代码推广 → 跑 dev → 报告；
  test 组最后跑一次。

## 12. 选型记录

出题方式考虑过三种：全人工标注（最可信但约 100 题需数天）、模型起草 + 程序核验 + 人工审定、
直接采用开源数据集题目（只适用于 KB6）。用户选定 **后两者组合**：自建库用模型起草并经用户审阅，
KB6 用数据集原题作外部金标准和算法对比主体。语料组织在“每组独立小语料”和“少量大知识库共享”之间
选定后者：更接近真实个人知识库，天然产生干扰与跨库隔离，演示也可直接使用。
